# สรุปโครงการพัฒนา AI Chatbot บน Streamlit พร้อมงานวิจัยที่เกี่ยวข้อง

ฉบับรวบรวมความต้องการของระบบ แนวทางพัฒนา สถาปัตยกรรม เทคโนโลยี และเอกสารวิจัย — 12 ตุลาคม 2569

## 1. ภาพรวมโครงการ

โครงการนี้มีเป้าหมายพัฒนา แชตบอทภาษาไทยที่ตอบคำถามโดยอ้างอิงเฉพาะข้อมูลจาก Dataset ที่กำหนด สามารถตรวจสอบหลักฐานของคำตอบได้ และแสดงรูปภาพประกอบที่สัมพันธ์กับคำถามทุกครั้งที่ตอบ

ระบบจะพัฒนาบน Streamlit เชื่อมต่อกับ GitHub Repository เพื่อจัดเก็บโค้ด เอกสาร และรูปภาพที่เตรียมไว้ล่วงหน้า

จุดเด่นคือการรวมเทคนิค Retrieval-Augmented Generation (RAG), Semantic Search, Adaptive Chunking, Evidence Verification และ Image Retrieval เข้าด้วยกัน

ระบบไม่ได้มุ่งเพียงสร้างคำตอบที่ดูถูกต้อง แต่ต้องสามารถแสดงได้ด้วยว่า ข้อความแต่ละส่วนมาจากเอกสารใด หน้าใด และตำแหน่งใด พร้อมเลือกภาพที่ตรงกับระดับความลึกของคำถาม

หากบางส่วนของระบบต้องการความตรงกับ Dataset แบบเคร่งครัด สามารถใช้ Extractive Answering คือดึงคำตอบจากข้อความต้นฉบับโดยตรง แทนให้ AI เรียบเรียงอย่างอิสระ

## 4. ระบบค้นหาและเลือก Chunk ที่แม่นยำ

ปัญหาที่คุณระบุไว้มีสองส่วนซึ่งต้องแก้พร้อมกัน

ปัญหาแรก: ดึงข้อความมาเกินความจำเป็น

สมมติเอกสารมีสามหัวข้อ แต่คำถามต้องการเพียงหัวข้อที่สอง หากระบบดึงมาทั้งสามหัวข้อ จะทำให้เปลือง Context และอาจรบกวนการตอบ

ปัญหาที่สอง: ข้อความสำคัญถูกตัดขาด

หาก Chunk ถูกแบ่งกลางประโยคหรือถูกตัดเพราะเกิน Token Budget ระบบอาจได้หลักฐานที่ไม่ครบ ส่งผลให้ตอบผิดหรือตอบไม่สมบูรณ์

### วิธีแก้ไขที่เหมาะสม

- ใช้ Semantic/Structure-aware Chunking แบ่งข้อมูลตามความหมาย หัวข้อ และโครงสร้างเอกสาร
- ใช้ Vector Retrieval คัดเลือก Chunk ที่ใกล้เคียงคำถาม
- ใช้ Reranker ตรวจสอบความเกี่ยวข้องอีกครั้ง
- ใช้ Evidence Span Extraction เลือกเฉพาะประโยคหรือช่วงข้อความที่จำเป็น
- ใช้ Token Budget Controller จัดสรรพื้นที่ให้หลักฐานโดยไม่ตัดข้อความสำคัญแบบสุ่ม
- ใช้ Evidence Verification ตรวจสอบว่าหลักฐานเพียงพอก่อนตอบ

### ตัวอย่างงบประมาณ 2,048 Tokens

สมมติกำหนดให้ 2,048 Tokens เป็นพื้นที่รวมสำหรับการสร้างคำตอบหนึ่งครั้ง

ตัวอย่างการจัดสรร Context Budget

System + คำถาม

300 tokens

ข้อความหลักฐาน

1,250 tokens

ข้อมูลอ้างอิง

100 tokens

คำตอบ + สำรอง

398 tokens

ตัวเลขนี้เป็นตัวอย่างการออกแบบ ไม่ใช่ข้อกำหนดตายตัวของโมเดล และต้องวัดด้วย Tokenizer ที่ใช้งานจริง

เทคนิคนี้ช่วยให้ควบคุมต้นทุนและลดข้อความส่วนเกิน แต่ต้องทดสอบด้วยว่าการลดจำนวน Tokens ไม่ทำให้ข้อมูลสำคัญหายไป

## 5. ระบบตอบคำถามที่ยึด Dataset และตรวจสอบหลักฐาน

ข้อกำหนดที่สำคัญคือ ระบบห้ามนำความรู้ภายนอก Dataset มาเติมข้อเท็จจริงในคำตอบ แม้ LLM จะรู้เรื่องนั้นจากการฝึกโมเดลก็ตาม

ผมแนะนำให้แยกการตอบออกเป็นสองรูปแบบ

| รูปแบบ                 | วิธีการ                                | เหมาะกับ                              |
| ---------------------- | -------------------------------------- | ------------------------------------- |
| Extractive QA          | ดึงข้อความจาก Dataset โดยตรง           | ข้อมูลเฉพาะเจาะจง ตัวเลข ชื่อ ระเบียบ |
| Grounded Generative QA | เรียบเรียงคำตอบจากหลักฐานที่ตรวจสอบได้ | คำถามอธิบาย สรุป เปรียบเทียบ          |

สำหรับรูปแบบที่สอง ต้องตรวจสอบว่าทุกข้อความที่เป็นข้อเท็จจริงมีหลักฐานสนับสนุนจริง หากไม่มีหลักฐานให้ปฏิเสธการตอบ ไม่ควรเดาหรือค้นหาข้อมูลจากอินเทอร์เน็ตเพิ่มเติมโดยอัตโนมัติ

## 6. ระบบค้นหาภาษาไทย คำสะกดผิด และภาษาคาราโอเกะ

คุณต้องการให้ผู้ใช้สามารถค้นหาได้อย่างเป็นธรรมชาติ แม้พิมพ์ผิดหรือใช้ตัวอักษรภาษาอังกฤษแทนภาษาไทย

ตัวอย่าง:

| คำถาม                   | ความหมายที่ต้องการ            |
| ----------------------- | ----------------------------- |
| `คุรุสาดคอม`            | ครุศาสตร์คอมพิวเตอร์          |
| `ครุศาสตร์คอมเรียนไร`   | ครุศาสตร์คอมพิวเตอร์เรียนอะไร |
| `rian computer tee nai` | เรียนคอมพิวเตอร์ที่ไหน        |
| `วิธีคูนเลข`            | วิธีคูณเลข                    |
| `10 kun 10`             | 10 คูณ 10                     |

ระบบควรใช้ Query Normalization ร่วมกับ Semantic Retrieval โดยเก็บทั้งข้อความที่ผู้ใช้พิมพ์จริงและข้อความที่ระบบตีความไว้ ไม่ควรแทนที่ข้อความเดิมทั้งหมด เพราะการแก้คำผิดอัตโนมัติอาจเปลี่ยนเจตนาของผู้ใช้

## 7. ระบบเลือกรูปภาพประกอบอัตโนมัติ

นี่เป็นฟีเจอร์ที่คุณต้องการเพิ่มตามข้อกำหนดของหัวหน้า โดยมีหลักการว่า ทุกคำตอบที่ระบบตอบได้ต้องมีภาพประกอบจาก Dataset และภาพนั้นต้องสัมพันธ์กับสิ่งที่ผู้ใช้ถามจริง

ภาพทั้งหมดจะถูกเตรียมไว้ล่วงหน้า โดยคุณสามารถตัดภาพเองหรือให้ AI Agent ช่วยตัดรูปจากเอกสาร จากนั้นตรวจสอบและเก็บไว้เป็น `.webp` บน GitHub

### ตัวอย่าง Metadata ของรูปภาพ

```
{
  "image_id": "img_002",
  "file_path": "assets/images/math_10x10_explain.webp",
  "title": "การอธิบาย 10 คูณ 10",
  "description": "ตาราง 10 แถว 10 คอลัมน์ แสดงจำนวน 100 ช่อง",
  "keywords": ["การคูณ", "10x10", "100"],
  "image_type": "visual_explanation",
  "question_intents": ["explanation", "how", "why"],
  "source_document": "math.pdf",
  "source_page": 8,
  "bounding_box": [100, 200, 420, 520],
  "linked_chunk_ids": ["chunk_025"],
  "verified": true
}
```

ข้อมูลเหล่านี้ช่วยให้แชตบอทรู้ว่ารูปภาพคืออะไร เหมาะกับคำถามใด เชื่อมโยงกับข้อความไหน และมีต้นฉบับจากที่ใด

ค่า `verified` ควรตั้งเป็น `true` หลังผ่านการตรวจสอบจริง ไม่ควรถือว่า Caption ที่ AI สร้างขึ้นถูกต้องโดยอัตโนมัติ

## 10. การวางแผนทดลองและประเมินประสิทธิภาพ

ถ้าต้องการยกระดับโปรเจกต์นี้ให้เป็นงานวิจัย ไม่ควรประเมินเพียงว่าระบบตอบถูกกี่ข้อ แต่ต้องตรวจสอบประสิทธิภาพในแต่ละขั้นตอน

| ส่วนที่ทดลอง            | วิธีวัดผล                                         |
| ----------------------- | ------------------------------------------------- |
| การค้นหา Chunk          | Precision\@k, Recall\@k, MRR                      |
| คุณภาพ Chunk            | ความครบถ้วนของหลักฐานและสัดส่วนข้อความส่วนเกิน    |
| Context Management      | จำนวน Tokens ที่ใช้ และอัตราหลักฐานสำคัญที่ตกหล่น |
| ความถูกต้องของคำตอบ     | Answer Accuracy, Faithfulness                     |
| ความถูกต้องของ Citation | Citation Precision, Citation Recall               |
| การเลือกภาพ             | Image Relevance\@1, ความถูกต้องของประเภทภาพ       |
| ภาษาคาราโอเกะและคำผิด   | Retrieval Recall แยกตามประเภทคำถาม                |
| ประสิทธิภาพระบบ         | Response Time, Memory Usage                       |
| UX                      | ความสะดวกในการค้นหาและตรวจสอบหลักฐาน              |

## 11. แผนพัฒนาระบบตามลำดับ

ระยะที่ 1 — Dataset และระบบอ้างอิง

เตรียมเอกสาร แยกข้อความ แบ่ง Chunk จัดเก็บตำแหน่งหลักฐาน และสร้าง Text Embeddings ให้ค้นหาได้ก่อน

ระยะที่ 2 — Retrieval และ Context Optimization

เพิ่ม Reranking, Adaptive Evidence Selection และ Token Budget Controller พร้อมตรวจสอบความครบถ้วนของหลักฐาน

ระยะที่ 3 — ระบบรูปภาพจาก GitHub

ครอปภาพ แปลงเป็น WebP เพิ่ม Metadata เชื่อมกับ Chunk และสร้างระบบเลือกรูปภาพตามคำถาม

ระยะที่ 4 — การรองรับภาษาไทยรูปแบบต่าง ๆ

เพิ่มระบบจัดการคำสะกดผิด ภาษาคาราโอเกะ และทดสอบความแม่นยำของ Semantic Search

ระยะที่ 5 — UI, Highlighting และ Animation

สร้างหน้าต่างแสดงหลักฐาน เลื่อนไปยังข้อความต้นฉบับ และปรับประสบการณ์ใช้งานให้ลื่นไหล

ระยะที่ 6 — การทดสอบเชิงวิจัย

เปรียบเทียบวิธี Retrieval, Chunking และ Image Selection เก็บผลทดลอง วิเคราะห์ข้อผิดพลาด และสรุปประสิทธิภาพของระบบ

## สรุปข้อเสนอสำหรับโปรเจกต์

ผมมองว่าระบบนี้มีความเป็นไปได้ในการพัฒนาจริง และสำหรับ Streamlit ที่เชื่อม GitHub อยู่แล้ว แนวทางที่เหมาะสมคือ เตรียม Dataset, Chunk, รูป WebP และ Metadata ล่วงหน้า แล้วให้ระบบค้นหาและเลือกรูปจากสิ่งที่จัดเก็บไว้ ไม่ต้องประมวลผลเอกสารต้นฉบับใหม่ทุกครั้งที่มีคำถาม

ส่วนที่ควรลงทุนกับการวิจัยมากที่สุดคือ การเลือกหลักฐานข้อความและรูปภาพอย่างสัมพันธ์กันภายใต้ข้อจำกัด Context Budget เพราะเป็นส่วนที่เชื่อมปัญหาทั้งหมดของคุณเข้าด้วยกัน ทั้งความตรงของคำตอบ ความประหยัด Tokens คุณภาพภาพประกอบ และความสามารถในการตรวจสอบย้อนหลัง

หากจัดลำดับความสำคัญ ผมแนะนำให้ทำระบบ ตอบจาก Dataset พร้อมตรวจสอบหลักฐานให้ถูกต้องก่อน จากนั้นค่อยเพิ่ม Image Retrieval การรองรับภาษาคาราโอเกะ และ Seamless UI ตามลำดับ เพื่อให้ทุกฟีเจอร์มีพื้นฐานความถูกต้องที่ตรวจสอบได้ครับ
