# ค่าทางเทคนิคของ Sorty: อธิบายแบบเข้าใจง่าย

ตรวจเทียบกับโค้ด ข้อมูลหนังสือ และสถานะ embedding ใน working tree เมื่อ 13 ตุลาคม 2026 เอกสารนี้แยก **ค่าที่โค้ดตั้งไว้**, **ค่าที่วัดได้จากข้อมูล**, **ข้อกำหนดจากผู้ให้บริการ** และ **ค่าที่ยังไม่ได้ทดลองปรับเทียบ** ออกจากกัน เพื่อไม่ให้เข้าใจว่าทุกตัวเลขผ่านการทดลองหาค่าที่ดีที่สุดแล้ว

## มองภาพรวมก่อน

นึกว่า Sorty เป็นผู้ช่วยในห้องสมุด:

1. ผู้ใช้ถามคำถาม
2. Gemini อ่านคำถามก่อน เลือกว่าจะดึงตรงหรือตีความก่อนค้น และส่งคำค้นอังกฤษกับ ID หัวข้อที่เกี่ยวข้อง
3. ระบบค้นหัวข้อและข้อความจริงในหนังสือ; หากต้องเลือกช่วงเนื้อหา ให้ Gemini เลือกเฉพาะ ID และบรรทัดจากรายการที่ค้นได้
4. ระบบตรวจและแสดงข้อความต้นฉบับพร้อมหลักฐาน และแปลเมื่อผู้ใช้เปิดการแปล

AI ไม่ได้แต่งคำตอบจากความจำแล้วอ้างว่าเป็นข้อความในหนังสือ การค้นคำและการเลือกหลักฐานเป็นคนละขั้น: ถ้าขั้นค้นไม่ส่งย่อหน้าที่ถูกต้องมาให้ AI ขั้นเลือกก็หยิบย่อหน้านั้นไม่ได้

## วิธีอ่านเหตุผลของตัวเลข

- **ตั้งในโค้ด** หมายถึงเป็นค่าที่โปรแกรมกำหนดไว้
- **วัดจากข้อมูล** หมายถึงเป็นผลจาก PDF และกติกาแบ่งข้อความ ไม่ใช่ค่าที่ตั้งเป้าไว้
- **ค่าแนะนำจากผู้ให้บริการ/งานวิจัย** หมายถึงมีหลักฐานทั่วไป แต่ยังไม่เท่ากับผลทดลองกับหนังสือของ Sorty
- **ยังไม่ปรับเทียบ** หมายถึงเรารู้ว่าค่าอยู่ตรงไหนในโค้ด แต่ยังไม่มีผลทดลองบอกว่าดีกว่าค่าที่ต่ำหรือสูงกว่า

เมื่อเอกสารบอกว่า “ถ้าต่ำกว่าจะเกิดอะไร ถ้าสูงกว่าจะเกิดอะไร” นั่นอธิบายผลที่คาดจากการทำงานของระบบ ไม่ได้หมายความว่าเราได้ทดลองทุกค่าจนครบ

## 1. โมเดลข้อความและการตั้งค่า AI

โมเดลข้อความที่ environment นี้โหลดอยู่คือ **gemini-3.5-flash-lite** โดยโค้ดอนุญาตให้เปลี่ยนโมเดลผ่านตัวแปรตั้งค่าได้ ถ้าเปลี่ยนโมเดลต้องทดสอบการคืน JSON การเลือกบรรทัด และคุณภาพคำแปลซ้ำ ไม่มีผลทดลองในโครงการนี้ที่พิสูจน์ว่าโมเดลนี้ดีกว่าทางเลือกทุกตัว

### Temperature = 0

Temperature ควบคุมความหลากหลายของคำตอบจากโมเดล ค่า **0** ลดความสุ่ม เหมาะกับงานที่ต้องคืนรูปแบบ JSON และเลือก ID/ช่วงบรรทัดตามต้นฉบับ

- **ทำไมใช้ 0:** ต้องการผลที่ตรงรูปแบบและไม่สร้างตัวเลือกหลากหลายโดยไม่จำเป็น
- **ถ้าต่ำกว่า:** ใช้ไม่ได้ เพราะ 0 เป็นค่าต่ำสุดของการตั้งค่านี้
- **ถ้าสูงกว่า 0:** ผลอาจหลากหลายขึ้น แต่ก็มีโอกาสเลือกช่วงต่างกันหรือคืน JSON ที่จัดการยากขึ้น
- **ข้อจำกัด:** ยังไม่มีการทดลองเทียบ Temperature หลายค่าใน Sorty และค่า 0 ไม่รับประกันว่า AI จะเลือกหลักฐานถูกหรือแปลไม่ตกหล่น

### เพดานข้อความที่ AI ส่งกลับ

**Max output tokens** คือความยาวสูงสุดของคำตอบที่โมเดลส่งกลับ ไม่ใช่จำนวน token ที่ระบบใช้ทุกครั้ง และไม่ใช่เพดานความยาวข้อความที่ส่งเข้าโมเดล หนึ่ง token อาจเป็นส่วนหนึ่งของคำ ไม่จำเป็นต้องเท่ากับหนึ่งคำหรือหนึ่งตัวอักษร

| งาน | เพดานปัจจุบัน | ทำไมใช้ค่านี้ | ถ้าต่ำกว่าหรือสูงกว่า |
|---|---:|---|---|
| ตีความคำถามและเลือกเส้นทางค้น | **1,200 tokens** | Gemini ต้องเลือก direct/interpret/out_of_scope และคืนคำค้นอังกฤษที่รักษาเงื่อนไข พร้อม ID หัวข้อจริงใน JSON; ใช้ก่อนค้นทุกคำถามเนื้อหา | ต่ำกว่านี้เสี่ยงผล JSON/คำค้นไม่ครบ สูงกว่านี้เพิ่มเพดานการใช้ token ค่านี้เป็นนโยบายเพื่อเผื่อผลลัพธ์ ยังไม่ได้ทดลองหาค่าที่ดีที่สุด; utility แปล query เดิม 400 tokens ไม่อยู่ในเส้นทาง submit ปัจจุบัน |
| เลือกหลักฐานจาก PDF | **1,800 tokens** | AI ต้องคืนชนิดคำถามกับรายการ ID และช่วงบรรทัด ซึ่งเลือกได้ไม่เกิน **8 ช่วง** | ต่ำกว่านี้อาจไม่พอสำหรับ JSON ที่มีหลายช่วง; สูงกว่านี้เพิ่มเพดานการใช้ token แต่ไม่ได้ทำให้เลือกถูกขึ้นเอง ยังไม่มีการเทียบเพดานอื่น |
| แปลข้อความหลักฐานที่กำลังแสดง | **6,000 tokens** | ข้อความที่แปลอาจประกอบด้วยหลายย่อหน้าที่ผู้ใช้กำลังอ่าน | ต่ำกว่านี้เพิ่มความเสี่ยงที่คำแปลยาวจะไม่ครบ; สูงกว่านี้เพิ่มความยาวสูงสุดและโอกาสใช้ token มากขึ้น ไม่มีผลทดลองยืนยันว่าค่านี้เหมาะที่สุด |

เพดานทั้งสามเป็น **ขีดจำกัดสูงสุด** ไม่ใช่โควตาที่ถูกใช้หมดทุกครั้ง หากคำแปลไม่ผ่านการตรวจเครื่องหมาย ตัวเลข หรือโครงสร้างที่ระบบคุ้มครอง ระบบจะคงต้นฉบับภาษาอังกฤษไว้แทน การตรวจนี้ช่วยป้องกันความเสียหายบางชนิด แต่ไม่ได้พิสูจน์ว่าความหมายไทยตรงกับอังกฤษ 100%

ระบบกำหนดให้คำตอบจากโมเดลเป็น JSON และปิด automatic function calling เพื่อให้โมเดลส่งข้อมูลตามรูปแบบที่โปรแกรมตรวจได้

ขั้นตีความส่งสารบัญที่มี ID จริงจาก dataset (วัดได้ 295 หัวข้อในชุดนี้) พร้อมคำถาม และประวัติคำถามที่ตอบแล้วล่าสุดไม่เกิน 2 ข้อ ค่า 2 จำกัดบริบทให้พอแก้คำอ้างย้อนอย่าง “แล้ววิธีนี้ล่ะ” และลดข้อมูลที่ส่ง ต่ำกว่านี้อาจขาดบริบท สูงกว่านี้เพิ่มต้นทุนและความเสี่ยงลากหัวข้อเก่ามาปน ยังไม่มีการทดลองเทียบจำนวนประวัติหลายค่า

Gemini API แต่ละขั้นมี timeout 20,000 มิลลิวินาที และลองสูงสุด 2 ครั้งเฉพาะสถานะชั่วคราว 429/500/502/503/504 เว้น 0.5 วินาทีก่อนครั้งที่สอง ค่า 2 กับ 0.5 เป็นการจำกัดเวลารอและจำนวนคำขอ ไม่ใช่ค่าที่พิสูจน์แล้วว่าดีที่สุด ลองน้อยกว่านี้ไม่รับมือเหตุชั่วคราว; ลองมากกว่านี้หรือเว้นนานขึ้นทำให้รอและอาจใช้โควตามากขึ้น SDK ถูกตั้งให้ทำครั้งเดียวในแต่ละรอบเพื่อไม่ให้เกิด retry ซ้อน ระบบยังยึด Gemini เป็นตัวตีความหลัก

## 2. การแบ่งหนังสือเป็น Chunk

**Chunk** คือชิ้นข้อความจากหนังสือที่ระบบใช้ค้น คล้ายการทำบัตรข้อความย่อยจากหนังสือเล่มใหญ่ Sorty พยายามแบ่งตามย่อหน้าและบรรทัดจริง แทนการตัดทุกจำนวนตัวอักษรโดยไม่ดูเนื้อหา

### เพดาน Chunk = 1,800 ตัวอักษร

โค้ดตั้งเพดานไว้ที่ **1,800 ตัวอักษร** และเมื่อย่อหน้ายาวเกินเพดาน ระบบแบ่งที่ขอบบรรทัด

- **ทำไมตั้งเพดาน:** จำกัดขนาดของชิ้นข้อความยาว เพื่อให้ค้นและส่งรายการให้ AI ดูได้โดยไม่รวมเนื้อหากว้างเกินไป
- **ถ้าต่ำกว่า:** จะมีชิ้นข้อความย่อยเพิ่ม และเนื้อหาที่อธิบายเรื่องเดียวกันอาจแยกออกจากกันมากขึ้น
- **ถ้าสูงกว่า:** อาจรวมเนื้อหากว้างขึ้นในชิ้นเดียว ซึ่งทำให้ผลค้นเฉพาะเรื่องได้ยากขึ้น แต่ก็อาจลดการแบ่งบางย่อหน้า
- **หลักฐานจากการทดลอง:** audit ทดลอง **900**, **1,800** และ **3,000 ตัวอักษร** กับคำถามอ้างอิง **16 ข้อ** ทั้งสามแบบได้ค่าเฉลี่ย page recall **1.00** ในชุดนั้น ค่า 900 ให้ **877 chunks** ส่วน 1,800 และ 3,000 ได้ **868 chunks** เท่ากัน
- **สรุปอย่างซื่อสัตย์:** 1,800 ทำให้ได้จำนวน chunks น้อยกว่าค่า 900 โดยไม่พบความต่างของ page recall ในชุดทดลองนี้ แต่ผลไม่ได้พิสูจน์ว่า 1,800 ดีกว่า 3,000 หรือเหมาะที่สุดกับทุกเอกสาร

คำถามอ้างอิง 16 ข้อเป็นชุดตรวจที่เตรียมไว้ ไม่ใช่ตัวแทนคำถามทุกแบบ ค่า recall 1.00 หมายถึงหน้าที่คาดหวังถูกค้นพบครบในชุดตรวจนี้ ไม่ได้หมายถึงระบบตอบถูกทุกคำถาม

### Overlap = 0

Overlap คือการคัดลอกข้อความท้าย Chunk ก่อนหน้าไปซ้ำใน Chunk ถัดไป Sorty ตั้งเป็น **0** จึงไม่ทำสำเนาบรรทัดซ้ำ

- **ทำไมใช้ 0:** ลดข้อความซ้ำและไม่ทำให้หลักฐานเดียวกันปรากฏหลายครั้ง
- **ถ้าสูงกว่า 0:** อาจช่วยให้คำที่อยู่ตรงรอยต่อปรากฏกับข้อความข้างเคียง แต่ทำให้ข้อมูลและผลค้นซ้ำมากขึ้น
- **ข้อแลกเปลี่ยน:** ระบบเก็บ paragraph ID ไว้ และขยายกลับไปเอาย่อหน้าเดิมเมื่อจำเป็น วิธีนี้ช่วยคืนบริบทโดยไม่ต้องทำสำเนาทุก Chunk
- **ข้อจำกัด:** ไม่มีการทดลองเปรียบเทียบ overlap หลายค่าในชุดข้อมูลนี้

### จำนวนและความยาวจริง

- **868 chunks:** เป็นจำนวนที่ได้จาก PDF ปัจจุบันและกติกาแบ่งข้อความ ไม่ใช่จำนวนที่ตั้งให้ครบตามเป้า การลดจำนวนอาจเกิดจากการรวมข้อความมากขึ้น; การเพิ่มอาจเกิดจากการแบ่งย่อยมากขึ้น จำนวนนี้เพียงอย่างเดียวไม่ได้แปลว่าข้อมูลหายหรือครบ ต้องดูการตรวจบรรทัดและตำแหน่งอ้างอิงด้วย
- **ความยาวเฉลี่ย 228.2 ตัวอักษร:** คำนวณจาก chunks ทั้งหมด เป็นค่าที่วัดได้ ไม่ใช่เป้าหมาย
- **Chunk ที่ยาวที่สุด 1,323 ตัวอักษร:** เป็นค่าที่วัดได้จากชุดปัจจุบัน จึงยังไม่มี Chunk ใดแตะเพดาน 1,800

ค่าเฉลี่ยและค่าสูงสุดเปลี่ยนได้เมื่อ PDF หรือกติกาแบ่งเปลี่ยน จึงไม่ควรเขียนว่าเป็นค่าคงที่ของโปรแกรม

## 3. การค้นและการเลือกหลักฐาน

### ผลค้นปกติสูงสุด 12 chunks

การค้นปกติมีค่าเริ่มต้น **limit = 12** หมายถึงส่งผลค้นคืนได้ไม่เกิน 12 ชิ้นในเส้นทางนั้น

- **ทำไมมีเพดาน:** จำกัดจำนวนผลที่ต้องจัดอันดับและตรวจต่อ
- **ถ้าต่ำกว่า:** รายการสั้นลงและอาจตรงประเด็นขึ้น แต่เสี่ยงตัดหลักฐานที่เกี่ยวข้องออก
- **ถ้าสูงกว่า:** มีโอกาสพบหลักฐานเพิ่ม แต่ก็เพิ่มข้อความที่ไม่เกี่ยวข้องและภาระขั้นถัดไป
- **ข้อจำกัด:** ยังไม่มีการทดลองเปรียบเทียบค่า 12 กับค่าข้างเคียงเพื่อหาจุดที่ดีที่สุด Exact heading search สามารถคืนลูกของหัวข้อทั้งหมดได้ จึงไม่ควรตีความว่า 12 เป็นเพดานของทุกเส้นทาง

### Candidate pool: 48 chunks หรือ 18,000 ตัวอักษร

ก่อนให้ AI เลือกหลักฐาน ระบบจำกัดรายการที่ผ่านการค้นไว้ไม่เกิน **48 chunks** และจำกัดข้อความต้นทางรวมไว้ไม่เกิน **18,000 ตัวอักษร**

เปรียบเหมือนบรรณารักษ์ค้นหนังสือมาเป็นกองหนึ่งก่อน แล้วให้ AI ช่วยเลือกจากกองนั้น:

- **ถ้าลด 48 หรือ 18,000:** AI อ่านข้อความน้อยลงและใช้ token น้อยลง แต่ย่อหน้าที่ตอบคำถามอาจถูกกันออกก่อนถึง AI
- **ถ้าเพิ่ม:** มีโอกาสให้ AI เห็นข้อความที่เกี่ยวข้องมากขึ้น แต่ prompt ยาวขึ้น ใช้ token และเวลาเพิ่ม และมีข้อความรบกวนมากขึ้น
- **ทำไมเลือกค่าปัจจุบัน:** เป็นขอบเขตในโค้ดเพื่อจำกัดรายการและขนาด prompt
- **ข้อจำกัด:** ไม่มีการทดลองแบบควบคุมที่ยืนยันว่า 48 และ 18,000 เป็นค่าที่ดีที่สุด กรณีที่ candidate pool ไม่มีย่อหน้าคำตอบเป็นข้อจำกัดที่ต้องวัดต่อ

18,000 นี้นับเฉพาะตัวอักษรของข้อความต้นทาง ไม่ใช่ token ทั้งหมดของ prompt คำสั่ง JSON และข้อมูลประกอบก็ใช้พื้นที่เพิ่มด้วย

### AI เลือกได้ไม่เกิน 8 ช่วง

แต่ละ “ช่วง” อาจมีหลายบรรทัด AI ส่ง ID ของ Chunk และบรรทัดเริ่มกับบรรทัดสุดท้ายกลับมา

- **ทำไมมีเพดาน 8:** จำกัดจำนวนรายการที่ selector จะส่งกลับให้โปรแกรมตรวจ
- **ถ้าต่ำกว่า:** คำตอบที่ต้องอาศัยหลายย่อหน้าอาจขาดส่วนประกอบ
- **ถ้าสูงกว่า:** ส่งผลลัพธ์ยาวและหลายช่วงขึ้น แต่เพิ่มภาระตรวจความซ้ำและความเกี่ยวข้อง
- **ข้อจำกัด:** ไม่มีผลทดลองยืนยันว่าควรเป็น 8 มากกว่าหรือน้อยกว่า

โปรแกรมตรวจว่า ID และบรรทัดที่ AI ระบุมีอยู่จริง ช่วงบรรทัดไม่ย้อนหรือซ้อนกัน และข้อความที่แสดงตรงกับข้อความต้นฉบับ

### BM25: k1 = 1.2 และ b = 0.75

BM25 เป็นวิธีค้นด้วยคำ ระบบดูว่าคำในคำถามปรากฏในข้อความใด และใช้จัดอันดับชิ้นที่น่าจะเกี่ยวข้อง

- **k1 = 1.2:** ควบคุมผลของการพบคำซ้ำ ค่าเล็กทำให้คะแนนจากคำซ้ำอิ่มตัวเร็วขึ้น; ค่ามากทำให้การพบคำซ้ำเพิ่มคะแนนต่อได้นานกว่า
- **b = 0.75:** ควบคุมการปรับคะแนนตามความยาวข้อความ ค่า 0 ไม่ปรับตามความยาว ส่วนค่า 1 ใช้การปรับเต็มที่ ค่า 0.75 เป็นค่าตั้งต้นที่ใช้ใน Lucene BM25
- **ทำไมใช้ค่านี้:** เป็น baseline ที่พบในระบบค้นทั่วไป ไม่ใช่ค่าที่ปรับจากชุดคำถามของ Sorty
- **ถ้าต่ำกว่าหรือสูงกว่า:** อันดับผลค้นจะเปลี่ยนตามน้ำหนักคำซ้ำและความยาวข้อความ แต่ยังไม่มี local benchmark บอกว่าทิศทางใดดีกว่าสำหรับหนังสือเล่มนี้

ในโค้ดมีตัวคูณ **2.2** ซึ่งเท่ากับ k1 + 1 เมื่อ k1 = 1.2 และมีค่า **0.25** ซึ่งเท่ากับ 1 - b เมื่อ b = 0.75 ทั้งสองเป็นส่วนของสูตร ไม่ใช่พารามิเตอร์ที่ปรับแยกกันในหน้าตั้งค่า

### Reciprocal Rank Fusion constant = 60

RRF ใช้รวม “อันดับ” จากรายการค้นหลายวิธี เช่น keyword กับ vector โดยไม่เอาคะแนนดิบของแต่ละวิธีมาเทียบกันตรง ๆ

- **ทำไมเป็น 60:** งานต้นฉบับของ RRF ระบุว่าเลือก k = 60 หลังการทดลองนำร่อง และพบว่าค่านี้ใกล้ค่าที่ดีในชุดข้อมูลของงานนั้น โดยการเลือกค่าไม่วิกฤตมาก
- **ถ้าต่ำกว่า:** ความต่างระหว่างอันดับบนกับอันดับล่างมีผลแรงขึ้น
- **ถ้าสูงกว่า:** ความต่างของอันดับมีผลแบนลง
- **ข้อจำกัด:** Sorty ใช้ค่า 60 ตามค่าตั้งต้นของวิธีนี้ แต่ยังไม่ได้ปรับเทียบกับคำถามของ Sorty และขณะไม่มี vector index ขั้นรวมอันดับนี้ไม่มีผลจาก vector

### Vector similarity threshold = 0.66

ระบบยอมรับ vector candidate เมื่อ similarity อย่างน้อย **0.66** และต้องมีคะแนน lexical มากกว่า 0 ด้วย

- **ถ้าต่ำกว่า:** ได้ candidate เพิ่ม แต่อาจมีข้อความใกล้เคียงน้อยหรือไม่ตรงคำถามมากขึ้น
- **ถ้าสูงกว่า:** คัดเข้มขึ้น แต่อาจตัด passage ที่เกี่ยวข้องออก
- **ทำไมเป็น 0.66:** เป็นค่าที่กำหนดไว้ในโค้ด แต่ไม่มีผลทดลองกับ vector index ของ Sorty รองรับว่าเป็นจุดที่เหมาะสม
- **สถานะ:** index ยังไม่สมบูรณ์ จึงยังไม่มีผลค้นจริงที่ใช้ threshold นี้ ควรถือเป็นค่าชั่วคราวจนกว่าจะสร้าง index และทดสอบ

## 4. Embedding และข้อจำกัดจากผู้ให้บริการ

**Embedding** คือการแทนข้อความด้วยชุดตัวเลข เพื่อให้เปรียบเทียบข้อความที่ใช้คำต่างกันแต่มีความหมายใกล้กันได้ คล้ายวางประโยคลงบนแผนที่ความหมาย แล้วดูว่าประโยคใดอยู่ใกล้คำถาม

### รุ่น embedding: gemini-embedding-001

โค้ดระบุรุ่นนี้สำหรับแปลงทั้งข้อความหนังสือและคำถามเป็นเวกเตอร์ รุ่นที่เลือกเป็นค่าปัจจุบันในโค้ด แต่ยังไม่มีผลเปรียบเทียบกับ embedding รุ่นอื่นบนข้อมูล Sorty จึงไม่ควรเรียกว่าเป็นรุ่นที่ดีที่สุดสำหรับโครงการ

โค้ดติดป้ายงานเอกสารเป็น RETRIEVAL_DOCUMENT และงานคำถามเป็น RETRIEVAL_QUERY เพื่อให้โมเดลทราบว่าข้อความแต่ละชุดใช้ทำหน้าที่ใด

### มิติ = 768

เวกเตอร์หนึ่งชุดมีตัวเลข **768 ค่า** จำนวนนี้เรียกว่า “มิติ” ไม่ใช่จำนวนคำหรือจำนวน token

- **ทำไมเลือก 768:** เอกสาร Google แนะนำขนาด 768, 1536 และ 3072 สำหรับรุ่นนี้ และระบุว่าขนาดเล็กลงช่วยลดพื้นที่จัดเก็บและงานคำนวณ โดยคุณภาพจาก benchmark ทั่วไปใกล้กับขนาดใหญ่ได้
- **ถ้าต่ำกว่า:** ใช้พื้นที่น้อยลง แต่ข้อมูลความหมายที่เก็บอาจลดลง
- **ถ้าสูงกว่า:** เก็บมิติมากขึ้น แต่ใช้พื้นที่และงานคำนวณมากขึ้น
- **ข้อจำกัด:** ข้อแนะนำและ benchmark ของ Google ไม่ได้พิสูจน์ว่าค่า 768 ให้ผลดีที่สุดกับหนังสือของ Sorty ต้องทดสอบกับคำถามของเราเอง

หลังได้เวกเตอร์ โค้ดปรับความยาวเวกเตอร์ให้อยู่ในหน่วยเดียวกันก่อนคำนวณ cosine similarity ซึ่งทำให้การเปรียบเทียบเน้นทิศทางของเวกเตอร์

### ขีดจำกัด input ของ embedding = 2,048 tokens ต่อข้อความ

นี่เป็นข้อกำหนดของรุ่น embedding ตามเอกสาร Google ไม่ใช่ค่าที่ตั้งใน Sorty และเพิ่มด้วยการแก้โค้ดอย่างเดียวไม่ได้

Chunk แบ่งด้วยจำนวนตัวอักษร แต่ข้อจำกัดนี้นับ token ตัวอักษรกับ token ไม่ได้เท่ากันเสมอ โค้ดปัจจุบันยังไม่มีการตรวจ token ของแต่ละ Chunk ก่อนส่งเข้า embedding ดังนั้นเพดาน 1,800 ตัวอักษร **ไม่ได้พิสูจน์** ว่าทุก Chunk ต่ำกว่า 2,048 embedding tokens

ค่า 2,048 อีกแห่งใน answer() เป็นคนละเรื่องกัน ดูหัวข้อ Token budget ด้านล่าง

### Batch = 24 chunks ต่อคำขอ

สคริปต์สร้างเวกเตอร์ครั้งละไม่เกิน **24 ข้อความ** และบันทึก checkpoint หลังชุดที่สำเร็จ

- **ทำไมใช้ 24:** ทำให้คำขอมีขนาดจำกัดและสามารถกลับมาทำต่อจากชุดที่บันทึกไว้ได้
- **ถ้าต่ำกว่า:** แต่ละคำขอเล็กลง แต่ต้องส่งคำขอมากขึ้นและใช้เวลารวมมากขึ้น
- **ถ้าสูงกว่า:** จำนวนคำขอลดลง แต่แต่ละคำขอใหญ่ขึ้นและอาจชนข้อจำกัดหรือ quota ได้ง่ายขึ้น
- **ข้อจำกัด:** ยังไม่มีการทดลองเปรียบเทียบ batch size หลายค่า จึงยังบอกไม่ได้ว่า 24 เป็นค่าที่เร็วหรือประหยัดที่สุด

ถ้าแบ่งข้อมูลปัจจุบัน 868 chunks เป็นชุดละ 24 จะต้องใช้ประมาณ **37 ชุด** เมื่อทุกชุดทำสำเร็จ ตัวเลขนี้เป็นการคำนวณจากขนาด batch ไม่ใช่จำนวนคำขอที่สำเร็จจริง

### สถานะจริง: 0 จาก 868 เวกเตอร์

ไฟล์สถานะปัจจุบันระบุว่าเริ่มคาดหวัง 868 เวกเตอร์ แต่สร้างสำเร็จ **0** และได้รับสถานะ provider **429**

- 0/868 เป็นค่าที่อ่านจากสถานะปัจจุบัน ไม่ใช่เป้าหมาย
- 429 เป็นรหัสตอบกลับจากผู้ให้บริการ โค้ดสถานะนี้ไม่ได้บอกสาเหตุละเอียดพอจะแยกว่าเป็น quota รายวันหรือ rate limit ประเภทใด
- เมื่อสร้างไม่ครบ ระบบยังไม่เผยแพร่ index บางส่วน และใช้การค้นหัวข้อ/คำสำรองแทน
- สถานะนี้ไม่ได้แปลว่า AI เลือกหลักฐานไม่ได้ทั้งหมด แต่การค้นเชิงเวกเตอร์ยังไม่มีข้อมูลให้ใช้

README มีตัวเลขเก่า 867 ขณะที่ Dataset และไฟล์สถานะปัจจุบันเป็น 868 เอกสารนี้จึงใช้ 868

## 5. Token budget ที่ชื่อ 2,048

ใน answer() มีค่าเริ่มต้น **budget = 2,048** โค้ดใส่ค่านี้ลงใน metadata พร้อมนับจำนวน token ของข้อความหลักฐานด้วย tokenizer ชื่อ cl100k_base

- **สิ่งที่ทำ:** บันทึกค่า limit และจำนวน source tokens ที่นับได้ในผลลัพธ์
- **สิ่งที่ไม่ได้ทำ:** ไม่ได้หยุดเลือกหลักฐานเมื่อนับถึง 2,048 และไม่ได้ตัดข้อความให้สั้นลง
- **เหตุผลที่ลดหรือเพิ่มไม่ได้:** ในโค้ดปัจจุบันค่านี้ไม่ได้ควบคุมการค้นหรือแสดงผล การเปลี่ยนจึงเปลี่ยนตัวเลข metadata แต่ไม่ได้ทำให้ Gemini รับ prompt ได้น้อยหรือมากขึ้น
- **ข้อควรระวัง:** cl100k_base เป็นวิธีนับที่โค้ดใช้ ไม่ใช่ตัวนับ token ของ Gemini โดยตรง

ดังนั้นอย่าเขียนว่า “Gemini มี input limit 2,048 tokens ในระบบนี้” ค่า 2,048 ตรงนี้เป็นข้อมูลนับ source text ส่วน input limit 2,048 ของ embedding เป็นข้อกำหนดจากเอกสารผู้ให้บริการและเป็นคนละค่าใช้งานกัน

โค้ดไม่ได้กำหนดเพดาน input tokens ของ prompt สร้างข้อความโดยตรง แต่จำกัดรายการหลักฐานไว้ 18,000 ตัวอักษร ซึ่งไม่เท่ากับเพดาน token

## 6. LLM ช่วยค้นแทน embedding ได้แค่ไหน

งานวิจัย Query2doc แสดงวิธีให้ LLM ขยายคำค้น แล้วส่งคำค้นที่ขยายไปค้นด้วย BM25 ได้โดยไม่จำเป็นต้องใช้ dense embedding ในขั้นค้น งานนั้นรายงานผลดีขึ้น **3–15%** บนชุดทดสอบ MS MARCO และ TREC DL ตัวเลขดังกล่าวเป็นผลของงานวิจัย ไม่ใช่ผลของ Sorty และยังยืนยันไม่ได้ว่าจะได้ผลเท่ากันกับ PDF นี้

ในโค้ด Sorty ปัจจุบัน:

- มีการแปลคำถามไทยเป็นอังกฤษในบางกรณี
- มี BM25/ค้นหัวข้อเพื่อสร้าง candidate pool
- มี LLM เลือกหลักฐานจาก candidate ที่ค้นได้
- **ยังไม่มีขั้น LLM query expansion แบบ Query2doc**

ดังนั้น Sorty ทำงานได้โดยไม่ใช้ embedding แต่ LLM ยังไม่ได้แทนการค้นทั้งเล่มด้วยตัวเอง หากจะเพิ่ม query expansion ควรเก็บคำถามเดิมไว้รวมกับคำที่ AI เสนอ แล้วค้นด้วย BM25 จากข้อความต้นฉบับเท่านั้น คำที่ AI สร้างเป็นเพียงตัวช่วยค้น ห้ามใช้เป็นหลักฐานคำตอบ

การเพิ่ม query expansion ใช้ token สร้างคำค้นต่อคำถาม แต่ไม่ต้องสร้างเวกเตอร์ล่วงหน้าให้หนังสือทั้งชุด ต้องวัดกับชุดคำถามเดิมว่า candidate recall ดีขึ้นจริงหรือไม่ รวมถึงตรวจ FP/FN และหลักฐาน PDF ทุกคำตอบ

## 7. สิ่งที่ตัวเลขพิสูจน์และยังพิสูจน์ไม่ได้

- audit ที่ใช้คำถามอ้างอิง 16 ข้อได้ mean page recall 1.00 หมายถึงหน้าที่คาดหวังถูกค้นพบครบโดยเฉลี่ยในชุดนั้น
- audit ตรวจ citation offsets ได้ **868/868 chunks** ว่าข้อความชี้กลับไปยังช่วงข้อความบนหน้าที่ถูกต้อง
- ตรวจบรรทัดเนื้อหาได้ **4,446/4,446** ตามชุดบรรทัดที่คาดว่าจะเก็บ

ตัวเลขเหล่านี้ตรวจ coverage และตำแหน่งอ้างอิง ไม่ได้พิสูจน์ว่า AI เลือกข้อความที่ตอบคำถามได้ตรงที่สุดทุกกรณี ไม่ได้วัดความถูกต้องของคำแปลครบทุกย่อหน้า และไม่ได้แทนการทดลองกับผู้ใช้จริง

มีผลทดลองเปรียบเทียบขนาด Chunk ตามที่อธิบายไว้ ส่วน Temperature, เพดาน output tokens, จำนวน candidate, BM25 k1/b, similarity threshold และ batch size ยังไม่มีการทดลองปรับค่าทีละตัวเพื่อหาค่าที่เหมาะที่สุด

### เอกสารและงานวิจัย

- Google, [Gemini Embedding model](https://ai.google.dev/gemini-api/docs/models/gemini-embedding-001) — input limit และขนาดเวกเตอร์ที่แนะนำ
- Apache Lucene, [BM25Similarity](https://lucene.apache.org/core/9_12_3/core/org/apache/lucene/search/similarities/BM25Similarity.html) — ค่าเริ่มต้น k1=1.2, b=0.75 และความหมายของพารามิเตอร์
- Cormack, Clarke, and Buettcher, [Reciprocal Rank Fusion](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf) — ที่มาของค่า k=60
- Wang, Yang, and Wei, [Query2doc: Query Expansion with Large Language Models](https://aclanthology.org/2023.emnlp-main.585/) — LLM ขยายคำค้นเพื่อช่วย BM25 และ dense retrieval
